# Pwn challenge corpus

Pwnx is validated against the authorized local corpus at
`PWNX_CHALLENGE_ROOT` (default:
`/Users/brandonli/Downloads/pwn-challenges`). The coverage source of truth is
[`corpus/coverage.csv`](../corpus/coverage.csv), generated from the corpus's
`CHALLENGES.csv`, `MANIFEST.csv`, and current filesystem.

The matrix records one row per curated challenge. Nested `dist/` copies and
identical artifacts are deduplicated while the curated source path remains
stable.

## Baseline

- Curated challenges: **131**
- Challenge directories with an existing solve/exploit: **111**
- Curated rows without any solve/exploit: **20**
- Verified pwnx solves: **2**
- Not yet converted to pwnx: **128**
- Artifact-missing placeholder rows: **1**
- Formats: **330 ELF64**, **20 ELF32**, **1 Windows PE** in the source audit
- Runtime material: **23 Docker**, **3 kernel VM**, **1 V8**, **1 Windows row**

Purpose families are non-exclusive because real challenges combine primitives.
The initial classifier identifies approximately:

- 60 stack/control challenges
- 40 ROP/gadget challenges
- 37 heap/allocator challenges
- 27 format-string challenges
- 13 shellcode/seccomp challenges
- custom protocol, signal, musl, Rust, race, VM, kernel, V8, and Windows outliers

Counts are regenerated by the harness; this document describes the initial
baseline rather than replacing the CSV.

## Commands

Regenerate the matrix:

```bash
PWNX_CHALLENGE_ROOT=/path/to/pwn-challenges \
python scripts/corpus.py inventory --output corpus/coverage.csv
```

Verify exact row coverage against `CHALLENGES.csv`:

```bash
python scripts/corpus.py check --json
```

Summarize progress:

```bash
python scripts/corpus.py status --json
```

Filter work queues:

```bash
python scripts/corpus.py list --priority critical
python scripts/corpus.py list --family heap --status not_started
```

Inspect a declared run without executing it:

```bash
python scripts/corpus.py run --id C015 --dry-run --json
```

Live execution is bounded by timeout and output limits. Docker execution uses
`--network none`; local execution removes proxy variables and sets
`PWNX_OFFLINE=1`. The harness never invents a remote endpoint or enables
network access implicitly.

## Matrix fields

Each row contains:

- stable ID, event, name, and curated path
- architecture and binary format
- deduplicated artifacts, binary, libc, loader, source, and Docker material
- existing solve and writeup paths
- non-exclusive purpose families
- pwnx solve path and implementation status
- native execution status and evidence
- precise missing primitive
- priority, environment, work directory, and JSON argv
- notes and deduplication evidence

`corpus/overrides.json` contains reviewed facts that cannot be inferred safely,
such as a real native execution result. Overrides may not add unknown fields.

## Initial priorities

Critical outliers are tracked explicitly instead of being called covered by a
generic ELF API:

- GreyCTF `dist-greynote`: kernel image/rootfs environment
- hxpCTF `kernel-rop`: kernel VM, KASLR/KPTI, and kernel ROP
- R3CTF `trustedhash`: kernel module, VM, TPM, and Rust protocol components
- SCTF `v8-pwn`: V8/JIT engine exploitation
- Sentinus `friendlytimeserver.exe`: Windows PE execution and debugging

High-priority rows are primarily missing solves/artifacts and educational
challenges useful for validating stack, format, heap, shellcode, and bytecraft
surfaces before the outlier adapters are expanded.

## Completion rule

A row is `verified` only after its pwnx solve executes against the real local
artifact or declared isolated runtime and records concrete evidence. Merely
having an existing pwntools solve, compiling a pwnx script, or matching a
template is not execution proof.
